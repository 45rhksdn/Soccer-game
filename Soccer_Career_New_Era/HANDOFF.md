## 2. 가장 중요한 주의 — 운영 사이트의 최신 Work 코드

- 0.3 ZIP은 운영 사이트(`soccer-career-new-era.spicy-vine-2764.chatgpt.site`)보다 오래된 스냅샷이다. 운영 화면에는 `선수 변경하기` 메뉴가 있었지만 ZIP에는 없었다.
- 이 브랜치의 `선수 변경하기`는 **ZIP을 기준으로 새로 구현**한 것이다. Work의 구현 코드를 본 적이 없으므로 동작·저장 키가 다를 수 있다.
- **이 브랜치를 운영 사이트에 그대로 배포하지 말 것.** 최신 Work 소스를 확보하면 `main`에 별도 커밋으로 올린 뒤 이 브랜치와 diff·병합한다. 두 구현의 저장 키(아래 4절)가 겹치거나 다르면 마이그레이션을 추가한다.
- **0.5 작업 시점(2026-10-17)에도 최신 Work 소스는 저장소에 없었다**(원격 브랜치: `main`, `claude/v0.3.1-fixes`, `claude/v0.4-traits-scouting`, `build/…`만 존재). 따라서 0.5는 **GitHub 기준 수정**이며 Work와 병합하지 않았다. 병합 시 확인할 항목:
  - 장비: Work에 장비 구매·장착이 있다면 이 브랜치의 `development.equipment {owned, equipped}`와 필드·가격·보너스를 맞추고 한쪽만 남긴다(기본 능력치는 `player.a`, 보너스는 분리 저장이 원칙).
  - 선수 변경하기·슬롯 삭제·교체 전 선수 복원의 저장 키(`slotN`/`backupN`/`archiveN`/`activeSlot`).
  - 은퇴 보상 키 `legacy`와 `Career.id`. Work 저장에 id가 없으면 v5→v6 변환처럼 생성 시 고정값으로 만든다.
  - 깨달음·럭키 확률, 노화 곡선이 Work에서 따로 바뀌었는지(이 브랜치는 `traits.ts` 상수 + `aging.ts`).

## 3. Work ↔ Claude 교대 규칙

1. 시작 전: `git pull`, 이 문서·CHANGELOG 읽기, `npm ci && npm test && npm run build`.
2. 작업은 새 브랜치에서, 기능별 커밋. 원본 전체 재작성·저장 데이터 초기화 금지.
3. 저장 형식을 바꾸면 `SAVE_VERSION`을 올리고 `storage.ts`의 `validate()`에 이전 버전 → 새 버전 변환을 **추가**한다(기존 단계 삭제 금지). `tests/fixtures/`에 이전 버전 실제 저장 파일을 남기고 변환 테스트를 쓴다.
4. 특성·학교를 추가할 때 기존 id는 절대 바꾸거나 재사용하지 않는다(저장에 id가 들어 있다).
5. 끝나면 이 문서의 체크리스트·테스트 결과·알려진 문제를 갱신한다.

## 4. 저장 형식 v6 (IndexedDB `soccer-career-new-era` / store `saves`)

| 키 | 내용 |
|---|---|
| `slot1..3` | 선수 커리어 (SCNE JSON 문자열, 체크섬 포함) |
| `backup1..3` | 해당 슬롯의 마지막으로 **달랐던** 저장. 읽을 수 없는 슬롯은 백업으로 옮기지 않음 |
| `archive1..3` | 새 선수로 교체되기 전의 선수(교체 전 선수). 자동 저장이 건드리지 않음 |
| `activeSlot` | 마지막으로 플레이한 슬롯 번호 |
| `scouting` | `{seed, lists:{[schoolId]:목록번호}}` 스카우트 상태(커리어와 분리) |
| `legacy` | **0.5** 계정 공통 은퇴 기록 `{version:1, retired:[{id,name,year,age,pos}]}` — 세 슬롯 공용, 커리어 안에 저장하지 않음 |

v5 → v6 변경 (0.5):
- `Career.id`: 선수 고유 id. 새 선수는 생성 때마다 새 id(`p-…`), 백업·교체 전 선수·파일 복원은 같은 id. v5 저장은 **생성 시 고정되는 값**(이름·포지션·체격·스타일·성장유형·학습효율·학교·라이벌 이름/학교·첫 성장 기록)으로 `legacy-…` id를 만든다 → 같은 선수의 예전 저장은 항상 같은 id(RNG 상태 `seed`는 플레이 중 바뀌므로 쓰지 않음).
- `development.equipment?: {owned:string[], equipped:{boots?,wear?,gear?}}` (선택). 기본 능력치는 계속 `player.a`.
- `world.clubs[].roster[].injuryWeeks?` (선택) NPC 부상.
- `Insight.base?` (경기 중 저장에만, 선택): 깨달음 한도 판단용 기본 능력치.

v4 → v5 변경 (0.4, 유지):
- `development.trait` → `development.traits`(배열, 최대 3), 라이벌도 같음, NPC `roster[].traits`(해시 결정), `Career.schoolRef?`. 알 수 없는 특성 id는 보존.

**호환성 한계:** 0.3 코드는 v4만, 0.4 코드는 v5까지만 읽는다. v6 저장은 0.4 이하에서 열리지 않는다. 반대 방향(v1~v5 → v6)은 자동 변환된다(0.3·0.4 코드로 만든 실제 저장 파일로 검증: `tests/fixtures/v4-*.json`, `v5-*.json`).

## 7. 알려진 문제와 설계상 결정

- 노화 모델 계수는 `aging.ts` 한 곳에 있다(`GROWTH_BY_CURVE`, `DECLINE`, `npcGrowthRate`, `PEAK_AGE=32`). 바꾸면 `npx tsx scripts/long-sim.ts`로 다시 확인할 것. `traits.ts`의 `agingDecline`은 예전 import 호환용(미사용).
- 장기 시뮬레이션의 32세 최고점은 **시즌 말 기준**이다. 33세 생일(새 시즌 시작)에 첫 감퇴가 적용된다.
- 경기 활약 잠재력 상승은 94까지다. 은퇴 보상으로 그보다 높게 시작한 잠재력은 더 이상 깎이지 않는다(0.4까지는 깎였음).
- 은퇴 보상은 후보 목록을 다시 만들 때 잠재력 값만 바뀐다(같은 목록에서 상한만 넓어짐). 이미 시작한 커리어는 바뀌지 않는다.
- 슬롯 삭제는 되돌릴 수 없다. 단, 교체 전 선수(`archiveN`)는 다른 선수라서 지우지 않는다.
- NPC 부상은 상세 경기가 아닌 리그 경기에도 주간 확률로 반영된다(경기 엔진을 돌리지 않는 경기 포함).
- 특성 `플레이메이커`/플레이 스타일 `플레이메이커`, 특성 `대기만성`/성장 유형 `대기만성형`은 서로 다른 시스템이다.
- 가상 고교 3곳의 `boost`는 화면에만 표시된다(0.3부터). 실제 고교를 고르면 소속 가상 구단 이름이 그 학교명으로 바뀐다.
- 운영 Work의 최신 변경과의 병합은 아직 하지 않았다(2절).
