# Claude Code Opus 개발 인수인계 지시문 — Soccer Career: New Era

당신은 ChatGPT Work에서 제작 중이던 `Soccer Career — New Era`의 후속 개발 책임자다. 제공된 ZIP은 2026-10-16 15:45 KST경 보관된 **v0.3 소스 스냅샷**이며, 현재 실행 사이트의 최종 코드와 다를 수 있다. 먼저 `handoff/AUDIT_STATUS.md`와 `README.md`, `ARCHITECTURE.md`, `GAME_DESIGN.md`, `ROADMAP.md`, `TEST_REPORT.md`를 읽어라.

**절대 금지**: 원본 코드 전체 재작성, 기존 저장/선수/세계/라이벌 정보 삭제, v4 세이브를 읽지 못하는 스키마 변경, 라이브 환경에 오래된 ZIP 무검증 덮어쓰기, 현재 사이트에 보이지만 ZIP에는 없는 ‘선수 변경하기’ 기능을 지우는 일.

## 0. 시작 단계 — 차이와 기초 품질 확인
1. 코드 디렉터리 및 구조와 현재 Git 상태 확인, 신규 브랜치 생성. ZIP 원본을 읽기 전용 기준으로 보존.
2. 패키지 설치(`npm ci`), `npm test`, `npm run build`, 브라우저 e2e 재현. 실패하면 환경 문제인지 회귀인지 구분해 기록.
3. 운영 사이트 `https://soccer-career-new-era.spicy-vine-2764.chatgpt.site` 에는 ‘선수 변경하기’라는 화면 문구가 보이지만, 이 ZIP에는 없다. 실제 최신 Work ZIP 또는 원본 저장소에 접근할 수 있다면 우선 확보해 diff하고 통합. 접근할 수 없으면 기존 ZIP을 기초로 별도 브랜치에서 작업하되 라이브 배포/통합은 금지.
4. 현재 구현 vs 미구현을 소스 위치와 테스트 기준으로 점검해 `HANDOFF.md`에 체크리스트 작성.

## 1. 최우선 P1 — 긍정·부정 특성 리뉴얼
기존 `src/development.ts`에는 `TRAITS=['천재','실전파','행운아']`, `Development.trait` 단일 문자열이 있고 신인 생성 시 무조건 정확히 한 개를 균등 부여한다. 다음 목표는 이와 다르다.
- 신규 선수(플레이어 후보·라이벌·NPC 공통) 특성은 독립적인 가중 추첨으로 **0~3개** 가질 수 있도록. 기본 등장 확률은 각각 약 6%, 강한 긍정/심각한 부정 특성은 약 3%로 설정 가능한 데이터 테이블로 구현. 정확한 수치는 데이터 테이블에서 튜닝할 수 있게 하며 테스트에서 장기 분포 검증. 동시 특성 충돌·중복은 막을 것.
- 긍정 특성은 초록색, 부정 특성은 빨간색으로 아이콘과 UI 구별. 이미지 자산이 없어도 고유 SVG/UI 아이콘으로 시작 가능. 색상만으로 구별하지 말고 텍스트와 접근성 레이블 추가.
- 기존 3특성은 효과 보존: 천재 훈련 성장 ×1.7; 실전파 30% 확률로 그 경기만 능력 ×1.3; 행운아 관련 확률 3%→9%.
- 부정 특성 `유리몸`: **훈련 시 피로 증가량 ×1.5**, **부상 확률 ×1.5**. 실제 훈련·경기 부상 경로를 코드에서 구분하고, 사용자가 요구한 범위 우선 적용 후 필요하면 명시적으로 설명. 사용자·라이벌·NPC 모두 일관되게 적용 가능한 효과 계산 계층을 설계.
- 좋은 특성과 나쁜 특성의 추가 종류를 각각 여러 개 창의적으로 설계하되 지나치게 강력한 조합 방지 및 레어티 분류/발동 조건·설명 표준화.
- 저장 마이그레이션: v4의 `development.trait`은 `traits:[...]`로 변환하되 기존 유저에게 부여된 특성은 무작위로 다시 뽑지 말 것. 기존 내보내기 JSON/체크섬/백업/3슬롯 및 진행 중 경기 재개 보존. 변환 후에도 같은 시드 재현성 검증.
- 분포 테스트(최소 수만 명), 유리몸 피로/부상 1.5배, 실전파 발동/능력 임시치, 저장 전후 동일성 및 기존 v4 이행 테스트 구현.

## 2. 우선 P2 — 실제 축구부 고교 지도·선수 발굴
- 기존 `SCHOOLS`는 3개 가상 고교(부산 해온고/서울 한울고/수원 청명고)뿐이다. 실제 한국 고등학교 축구부를 대상으로 지역별 목록 구축. **운영 사실을 확인할 수 있는 공개 출처, 기준일, 학교명, 소재지, 검증 상태를 저장**하고 확인되지 않은 학교를 임의로 실제 축구부라고 표기하지 말 것.
- 한국 지도 기반 선택 UI(선택 가능한 시·도 영역) + 지역/학교 검색·필터. 지도 시각화 외에도 목록으로 선택 가능해야 함. 아이폰 화면 크기와 키보드/접근성 지원.
- 학교를 선택하면 **실제 학생 개인정보·실제 실존 선수·초상·실제 로고를 사용하지 않고** 가상의 후보 선수 풀을 생성. 지역·학교가 실제라도 등장 선수/능력/특성/이름의 실재 관계를 암시하지 않도록 명확히 표시.
- 후보는 이름/나이/포지션/능력/잠재력(일부는 정찰 이후 확인 가능)/특성 등으로 다양하게 생성. 사용자가 후보 목록을 비교하고 **원하는 한 명을 직접 골라 커리어 시작**하게 변경. 새 후보 풀 생성 기능 제공.
- 단, 무한 재생성으로 최강 선수만 뽑는 문제가 생기므로 재생성 시 비용/횟수 제한, 세계 시드/생성 ID, 저장 유지 등 게임 밸런스 설계. 사용자가 요청하지 않은 강한 제약은 기본값으로 강제하지 말고 제안/옵션 처리.
- 현재 `school`은 0~2의 정수로 `storage.validate()`에서 검증하며 `world.newWorld()`가 기존 학교/리그에 결합되어 있다. 실학교 목록을 바로 인덱스로 치환하면 저장이 손상될 수 있으므로 **불변 schoolId/별도 학교 카탈로그 및 기존 3학교 호환 레이어**를 설계. 기존 세이브 마이그레이션 테스트 필수.
- 선수 후보 생성과 특성 분포에는 고정 시드로 재현 가능한 RNG. 후보 풀 생성/선택/저장/불러오기, 지역/학교 전환, 동일 후보 유지/새로고침, 3개 커리어 슬롯 간 독립성을 검증.

## 3. 최신 기능 통합 — 선수 변경하기
- 오래된 ZIP은 저장 관리에서 3슬롯과 새 커리어 생성만 지원한다. 최신 배포 화면에는 `선수 변경하기`가 보인다. 직접 최신 코드를 확보하여 **이미 구현되어 있다면 절대 중복 구현하거나 제거하지 말 것.**
- 신규 선수 시작과 기존 선수 전환이 각각 독립 저장되어야 하며 3개의 커리어 슬롯 사용성 보장, 자동저장 중 빠른 전환 레이스와 슬롯 덮어쓰기 여부를 테스트.
- 구현 불명 시 완료 판정하지 말고 증거/테스트 필요 항목으로 유지.

## 5. 개발 방식과 산출물
- 작업 순서: (A) 기초 분석+테스트, (B) 특성 다중/부정/빈도+마이그레이션, (C) 실제 고교 지역지도+가상 후보 생성/선택, (D) 최신 선수 전환 기능 통합 검증.
- 기능별 별도 커밋 및 테스트. 새로운 파일은 필요한 범위에서만 추가. 변경한 기능이 실제로 돌아가는 코드로 끝나게 할 것.
- 결과 제출: 바뀐 파일 목록, 실제 구현/미구현 표, 로컬 실행 방법, 테스트/빌드 실행 결과, 세이브 호환 검증, 알려진 이슈, 다음 담당자가 이어갈 `HANDOFF.md`, **소스 전체 ZIP**. API 키/비밀번호/개인정보는 제외.
- `Work` 사용량이 돌아와 병행 개발을 다시 시작할 수 있게 GitHub 브랜치/커밋 SHA를 명시하고, 최신 Work 변경과 병합 전에는 사용자 세이브 또는 운영 사이트에 영향을 주지 말 것.

먼저 현재 ZIP의 실제 파일들을 확인하고, 위 감사 결과가 맞는지 독립적으로 검증한 후 구현을 시작하라. 질문 없이 안전하게 진행 가능한 범위는 바로 개발하되 데이터 파괴 또는 설계 전환은 먼저 보고하라.
